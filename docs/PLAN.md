> שם המשחק עדיין פתוח לבחירה. בקוד הוא מוגדר במקום אחד בלבד (`src/config.ts`).
> מצב נכון ל־22.11.2026. חנוכה מתחיל ביום ו׳, 4.12.2026, כלומר נשארו כ־12 יום.

## א. ארכיטקטורה מומלצת

```
 טלפוני קבוצות (/play) ─┐                         ┌──────── Supabase (Free) ────────┐
 טלפון מנחה  (/host)  ─┼── HTTPS / WebSocket ───▶│ Auth: אנונימי לקבוצות, סיסמה למנחה │
 מחשב הקרנה (/screen) ─┘                         │ Postgres + RLS: מקור האמת         │
                                                  │ RPC (plpgsql): מכונת מצבים אטומית  │
                                                  │ Edge Function "game": בדיקה+ניקוד  │
                                                  │ Realtime: רק public_state          │
                                                  └──────────────────────────────────┘
 אתר סטטי: React + TypeScript + Vite על Cloudflare Pages (חינם)
```

**למה כך:**

| החלטה | סיבה |
|---|---|
| **פונקציות Postgres (RPC) לכל מעבר מצב** | כל פעולה היא טרנזקציה אחת עם נעילת שורה, ולכן לחיצה כפולה, שני מנחים או מירוץ בין טלפונים לא יוצרים מצב שבור. אין זמן אתחול קר, ואין עלות. |
| **Edge Function אחת לבדיקת תשובות** | מנוע הבדיקה כתוב ב־TypeScript אחד שנבדק ביחידה (נרמול עברית, זוגות בסדר, פאזל, הימור, גמר). רק הפונקציה, עם הרשאת service role, רואה את מפתחות התשובה. |
| **טבלת `public_state` אחת למסך ולטלפונים** | זו "תמונת מצב בטוחה" שנבנית בשרת ואין בה שום סוד. רק הטבלה הזו פתוחה לקריאה, והיא היחידה שמשודרת ב־Realtime. כך אין דרך לגלות תשובה דרך ה־API. |
| **ספר ניקוד (ledger) במקום עמודת ניקוד** | כל שינוי ניקוד נשמר כשורה עם `source_key` ייחודי, ולכן ניקוד כפול בלתי אפשרי ברמת המסד, ויש היסטוריה מלאה לכל תוצאה. |
| **זמן שרת בלבד** | `received_at = clock_timestamp()` בשרת. הטיימר בטלפונים מסונכרן לזמן השרת (דגימת RTT), והטלפון לא מחליט כלום. |
| **שלושה bundles נפרדים** | המסך לא מוריד בכלל את קוד המנחה. |

**חלופה שנשקלה:** Firebase. נדחתה, כי Supabase מאפשר טרנזקציות SQL אטומיות ו־RLS אמיתי, וכבר יש לך חשבון.

## ב. סכמת מסד הנתונים

### תוכן (לא נמחק באיפוס)
| טבלה | תפקיד |
|---|---|
| `task_templates` | מאגר משימות: סוג, הוראות, `public_content` (מוצג רק כשהסבב נפתח), משך, שיטת ניקוד, ניסיונות, מדיניות הגשה, סטטוס (`candidate/approved/backup/rejected`), דגל דמה |
| `private.task_secrets` | **מפתחות תשובה** בסכמה שאינה חשופה ל־API, עם `verified_at` (חובה למשחק אמיתי) |
| `game_templates` + `game_template_rounds` | תבנית משחק: בדיוק סבבים 1–9, וסבב 9 הוא תמיד הגמר |
| `hosts` | אילו חשבונות הם מנחים |

### מופע משחק (נמחק באיפוס דמה)
| טבלה | תפקיד |
|---|---|
| `game_instances` | מצב `demo`/`live`, סטטוס, קוד הצטרפות, סבב נוכחי, תצוגת מסך. **מופע פעיל אחד בלבד** (אינדקס ייחודי) |
| `rounds` | 9 שורות למופע: שלב, `ends_at`, זמן שנותר בהשהיה, תוכן שהועתק בפתיחה, פתרון שהועתק רק בחשיפה, פיינליסטים |
| `teams`, `team_devices` | קבוצה + טלפונים (קפטן אחד בדיוק, PIN להצטרפות טלפון שני) |
| `submissions` | הגשה לכל פריט/ניסיון. ייחודיות: `(team, round, item, attempt)` ו־`(device, client_request_id)` לאידמפוטנטיות |
| `bets` | הימור לפני חשיפה, עם בסיס וניקוד קודם מוקפאים |
| `score_events` | ספר הניקוד. `revealed=false` עד החשיפה |
| `finals` | חמישיית הגמר, שתי החלופות, הניתוח, הבחירה והמקומות |
| `game_events` | יומן פעולות |
| `public_state` | תמונת המצב הבטוחה למסך ולטלפונים |

### הרשאות
- **אנונימי (מסך):** קורא רק `public_state`, ומפעיל `server_time()` ו־`round_progress()`.
- **קבוצה (משתמש אנונימי):** לא קוראת אף טבלה ישירות (RLS מחזיר 0 שורות). הפעולות שלה: `team_register`, `team_join`, `team_get_state`, `team_place_bet`, והגשה דרך ה־Edge Function.
- **מנחה:** קורא הכול דרך RLS, וכותב **רק** דרך פונקציות `host_*` שמאמתות `hosts`.
- **service role (ה־Edge Function בלבד):** פונקציות `svc_*`, והוא היחיד שמקבל מפתח תשובה.

### זרימת מידע
1. המנחה לוחץ (למשל "פתיחת סבב"). `host_round_action` נועל את המופע, מעדכן את `rounds`, ובונה מחדש את `public_state` (הגרסה עולה ב־1). Realtime דוחף את השינוי למסך ולכל הטלפונים.
2. טלפון שולח תשובה ל־`/functions/v1/game`. שם `svc_record_submission` בודק קפטן, שלב, זמן מול `ends_at` + חסד, ניסיונות, נעילה, סדר ופסילה, ושומר. אחר כך המנוע בודק, ו־`svc_apply_grade` כותב ניקוד מוסתר.
3. המסך מושך כל 2 שניות את "x/y קבוצות שלחו". הגשות **לא** משודרות, כדי לא לחרוג ממגבלת 100 הודעות בשנייה של Realtime.
4. "חשיפה" מעתיקה את הפתרון ל־`rounds.solution_payload` ומסמנת את ניקוד הסבב כגלוי.

## ד. החלטות שממתינות לאישורך

1. **שם המשחק** (20 הצעות נשלחו בצ'אט).
2. **שמונת הסבבים וסדרם**, מתוך 10 המועמדים: 4, 5, 8, 9, 11, 13, 17, 26, 31, 35. הימור (31) צריך להגיע מאוחר.
3. **חידת השמש** (הגמר). התשתית מוכנה: קוד, טקסט או בחירה.
4. **נוסחת ההימור**: בסיס = ממוצע מעוגל למטה ל־100 (כבר ממומש כפרמטר). מה המסלולים והמכפילים? מה קורה לקבוצה שלא הימרה?
5. **נוסחאות פרסי הגמר**. ההצעה הממומשת: א׳ (דרמטית) מבטיחה שהמקום ה־5 שמנצח בגמר עוקף את המוביל שמסיים שני. ב׳ (מאוזנת) נותנת פרס של כ־50% מהפער. וגם: מה עושים בשוויון על קו העלייה למקום 5? (כרגע כל המשוויונות עולות, והמנחה מקבל אזהרה.)
6. **שוברי שוויון** בדירוג הסופי (כרגע: מקום בגמר ואז ניקוד בסבב האחרון).
7. **משקל כל סבב** (נקודות מרביות).
8. **ניקוד הפאזל לפי זמן** (הצעה ממומשת: ליניארי עם רצפה של 30%).
9. **בונוס מהירות** בספרינט: כן או לא.
10. **ניקוד "האמת או ההמצאה"**.
11. **הכספת**: 2 חידות ספרה נוספות, רמז הסדר, ומספר ניסיונות.
12. **זיכרון הנרות**: אם הנציג עומד עם הגב למסך, איפה מוצג הרצף? (כרגע: בטלפון.)
13. **משוב מיידי** (נכון/לא נכון) בכל סבב: באילו סבבים?
14. **מדיניות הגשה**: רק הטלפון הראשי (ברירת המחדל), או כל טלפון כשהראשון קובע?
15. **משימת הסרטון**: להמשיך לאב־טיפוס, או לעבור לגיבוי (34)?
16. **מספר טלפונים מרבי לקבוצה** (ברירת מחדל: 3).
17. **פרויקט Supabase**: בחשבון שלך כבר יש 2 פרויקטים פעילים (TeacherApp, edtech), וזה המקסימום ב־Free. צריך להשהות אחד, לפתוח ארגון נפרד, או לאשר להשתמש בקיים (לא מומלץ).
18. **תאריך האירוע ומספר הקבוצות הצפוי**.

## ה. מה כבר מומש ונבדק

- **מנוע** (`supabase/functions/_shared/engine`): נרמול עברית (ניקוד, אותיות סופיות, מקף, כתיב מלא/חסר, ה׳ הידיעה לפי בחירה) עם 5 קטגוריות התאמה, ותשובה "לא ודאית" לא מקבלת ניקוד אוטומטי. זוגות בסדר הנכון. פאזל 3×3 (ערבוב דטרמיניסטי מהלכים חוקיים, אימות פתירות, שחזור מהלכים). הימור עם רצפת אפס. דירוג עם שוויונות. שתי חלופות גמר עם ניתוח "מי עוקף את מי". בודק ייחודיות לחידת התאמה.
- **מסד נתונים**: 2 מיגרציות, RLS, 36 פונקציות, איפוס דו־שלבי (טוקן ל־90 שניות והקלדת "איפוס").
- **Edge Function** `game`: submit, grade_round, review, compute_finals.
- **ממשקים**: מסך (פתיחה, QR, ענן קבוצות, סבב, טיימר, התקדמות, טבלה, אלופה), מנחה (כל מחזור החיים כולל הכרעה בתשובות לא ודאיות ובחירת חלופת גמר), קבוצה (הרשמה, טלפון שני עם PIN, קלט לכל 10 הסוגים).
- **בדיקות**: 41 בדיקות יחידה, ו־55 בדיקות SQL על Postgres אמיתי (הרשאות, אידמפוטנטיות, ניקוד כפול, איחור, השהיה, חשיפה, איפוס).

**עוד לא נבדק:** ריצה מול Supabase אמיתי ועל טלפונים. זה השלב הבא אחרי החלטה 17.
